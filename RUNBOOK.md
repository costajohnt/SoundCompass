# SoundCompass run book

Everything you need to go from a fresh `git clone` on your Mac to a
running build on your iPhone. The app was originally written without a
compiler in the loop, then updated to compile cleanly against Xcode 26
and the iOS 26 SDK. The core fixes (GCC-PHAT sign convention, subband
magnitude clamping, deprecated API renames) are already applied — this
runbook reflects the current state.

## Step 0 — prerequisites

You need a Mac with:

- **Xcode 26+** from the App Store. Launch it once so it installs
  the command-line tools.
- **iOS and watchOS simulator platforms** — Xcode 26 ships the SDK
  but not the simulator runtimes. Install them from
  `Xcode → Settings → Components`, or via the CLI:
  ```bash
  xcodebuild -downloadPlatform iOS
  xcodebuild -downloadPlatform watchOS
  ```
  Each is ~8 GB.
- **Homebrew** — https://brew.sh
- An **Apple ID signed into Xcode** under `Settings → Accounts`. A
  free account is enough to sideload to your own device; a paid
  Developer Program account is only needed for TestFlight / App Store.
- A **physical iPhone** running iOS 18 or later. The Simulator will
  let you build, but the direction estimates will be meaningless there
  because it only exposes a mono microphone.
- Optional: a paired **Apple Watch** on watchOS 11+ for the
  companion app.

---

## Step 1 — clone and generate the Xcode project

```bash
git clone git@github.com:costajohnt/sandbox.git
cd sandbox/SoundCompass
brew install xcodegen
xcodegen generate
open SoundCompass.xcodeproj
```

**Why XcodeGen?** The `.xcodeproj` file is a fragile blob that shows
up poorly in diffs, so this repo doesn't check it in. Instead we
check in `project.yml`, and `xcodegen generate` produces the
`.xcodeproj` every time.

**You will need to re-run `xcodegen generate`** every time someone
changes `project.yml` (e.g. adds a new target or a new build
setting).

## Step 2 — run the unit tests first

**This is the most important step.** The tests are pure Swift, run
in a few seconds, and will surface any real bugs in the DSP / state
types before you touch real hardware.

In Xcode:

1. Select the `SoundCompass-iOS` scheme (top-left dropdown). This
   scheme excludes the watchOS targets so you can test without the
   watchOS platform installed.
2. Pick **iPhone 17 Pro** as the destination.
3. Press `⌘U`.

Or from the terminal:

```bash
xcodebuild test \
  -project SoundCompass.xcodeproj \
  -scheme SoundCompass-iOS \
  -destination 'platform=iOS Simulator,name=iPhone 17 Pro' \
  CODE_SIGN_IDENTITY=- CODE_SIGNING_REQUIRED=NO CODE_SIGNING_ALLOWED=NO
```

All 69 tests should pass. The DSP tests exercise GCC-PHAT, direction
estimation, subband filtering, front/back resolution, calibration
processing, and all state types with synthetic signals.

## Step 3 — configure signing and first device run

1. In Xcode, select the `SoundCompass` project in the navigator.
2. For each of the five targets (`SoundCompass`, `SoundCompassWatch`,
   `SoundCompassWatchWidgets`, `SoundCompassWidgets`,
   `SoundCompassTests`):
   - **Signing & Capabilities → Team:** your Apple ID.
   - **Bundle Identifier:** change to something unique under a
     domain you own (e.g. `com.yourname.soundcompass`,
     `com.yourname.soundcompass.watchkitapp`, etc.).
3. **Heads-up:** these changes live in the `.xcodeproj` file, which
   is regenerated by XcodeGen. Bake your bundle prefix into
   `project.yml` (recommended — find-replace
   `com.soundcompass.app` with your own prefix) so you don't have
   to redo this each time you re-run `xcodegen generate`.
4. Plug in your iPhone. Trust the computer when prompted. Select
   the iPhone as the destination in Xcode's top bar.
5. Build and run (`⌘R`).
6. First launch will prompt for **microphone** permission, then
   **motion & fitness** permission. Grant both.
7. If you get a *"Could not launch — not trusted"* error on the
   device, go to **Settings → General → VPN & Device Management**
   on the phone and trust your developer certificate.

## Step 4 — smoke-test on real hardware

Hold the phone flat in your palm, screen up, the top edge of the
phone pointing the direction you're facing — the compass is
calibrated for that orientation.

Tap **Start listening** and run through this checklist:

- [ ] Clap your hands to your **right**. The arrow should swing right.
- [ ] Clap to your **left**. Arrow swings left.
- [ ] Have someone speak from **behind** you. The front/back banner
      under the compass should prompt you to rotate. Turn your body
      ~30° clockwise. Within a second or two the banner should
      commit to either **"Sound is in front of you"** or
      **"Sound is behind you"**.
- [ ] Open **Settings** (gear icon, top-right) →
      **Calibration trace…**. Tap **Record 5 seconds** while a
      sound source is running. A direction-over-time line chart
      should appear when the recording finishes.
- [ ] Tap the **clock icon** (top-left of the header) to open
      **Recent sounds**. Classifier labels should be accumulating
      as you make noise around the phone.
- [ ] Plug in wired or Bluetooth headphones. In Settings, set
      **Hearing ear** to whichever ear you actually hear with, and
      toggle **Audio passthrough** on. The phone should start
      streaming the room audio into your good-ear channel. **This
      is the CROS feature — the most useful thing for an SSD user.**
      If you don't have headphones, the toggle is a no-op by
      design.
- [ ] Trigger Siri: *"Hey Siri, start SoundCompass"*. The app
      should launch and begin listening.
- [ ] Lock your phone while listening. A Lock-Screen Live Activity
      (or Dynamic Island display on iPhone 14 Pro+) should appear
      with the compass direction and current loudness.
- [ ] On a paired Watch, the SoundCompass companion should show a
      mirrored compass. Add a complication from a watch face for
      a glance view.

## Step 5 — when something breaks

Report back with:

- The exact error text from Xcode's **Issue Navigator** or the
  latest build log in the **Report Navigator**.
- The failing file and line number.
- On hardware: whether the failure was a crash, wrong arrow
  direction, silence, a banner that never flipped, or something
  else.

### Issues found and fixed during the Xcode 26 upgrade

The following issues were found during the first compiler pass and
are already fixed in the current code:

1. **`GCCPHAT.estimateLag` sign convention** — the lag sign was
   flipped. Fixed by negating the return value (`-bestLag`).
   This was the predicted risk #1 from the original runbook.
2. **`SubbandDirectionEstimator` dominant-band comparison** — the
   `min(combined * 8, 1.0)` clamping in `DirectionEstimate.magnitude`
   made all loud bands compare as equal (all clamped to 1.0). Fixed
   by adding `combinedRms` to `DirectionEstimate` and using the raw
   RMS for inter-band comparison.
3. **`HelpSheet` body collision** — `HelpSection` had a stored
   property `body` (the FAQ text) and a computed property `body`
   (SwiftUI's `View.body`). Renamed the stored property to `content`.
4. **`SessionStats` Self reference** — `Self.emptySnapshot()` in a
   stored property initializer is not allowed in Swift. Changed to
   `SessionStats.emptySnapshot()`.
5. **`CalibrationClip` Equatable** — SwiftUI's `onChange(of:)` requires
   `Equatable`. Added conformance.
6. **Charts axis format ambiguity** — `AxisValueLabel(format: .number...)`
   was ambiguous. Disambiguated with explicit `FloatingPointFormatStyle`.
7. **`.allowBluetooth` deprecated** — renamed to `.allowBluetoothHFP`
   in `AudioDirectionDetector` and `CalibrationRecorder`.
8. **watchOS ActivityKit import** — `SoundCompassWatch` target was
   pulling in `Shared/SoundCompassActivityAttributes.swift` which
   imports `ActivityKit` (unavailable on watchOS). Fixed by listing
   only the specific shared files the watch target needs.

### Areas still worth watching on real hardware

- **`PassthroughMixer.connect`** — calls
  `engine.connect(inputNode, to: mainMixerNode, format:)` while an
  `installTap` is also on the input node. Should work because taps
  aren't graph edges, but needs real-hardware confirmation.
- **`SNClassifySoundRequest(classifierIdentifier: .version1)`** —
  compiles and links fine, but the built-in classifier may not be
  available on all device configurations.
- **Bluetooth headsets** deliver mono, making direction estimation
  impossible. The UI surfaces a warning.

## Step 6 — iteration loop

```bash
# Pull any fixes
git pull

# If project.yml changed, regenerate the Xcode project
cd SoundCompass
xcodegen generate

# Re-run tests
⌘U
```

If `project.yml` changes (new target, new build setting, new source
file), **you must re-run `xcodegen generate`** before building.

## Step 7 — shipping to TestFlight (later, not now)

Only do this after steps 0–6 are solid and the app actually works on
your device. Requires a paid Apple Developer account.

1. Set all five targets' bundle identifiers under your team prefix
   in `project.yml`, then `xcodegen generate`.
2. Bump `MARKETING_VERSION` / `CURRENT_PROJECT_VERSION` in
   `project.yml`.
3. Replace the placeholder `AppIcon.appiconset` in
   `SoundCompass/Assets.xcassets` with real 1024×1024 PNG icon
   artwork.
4. In Xcode: `Product → Archive`. Wait for the build. Organizer
   opens. **Distribute App → TestFlight & App Store**.
5. In App Store Connect, fill out the privacy questionnaire. Most
   answers are *"no"* — nothing leaves the device. The one
   exception is `UserDefaults` and `SystemBootTime`, and those are
   already declared in `SoundCompass/PrivacyInfo.xcprivacy`.

## Architecture cheat sheet

See `ARCHITECTURE.md` for the full map. Quick version:

```
SoundCompass.xcodeproj (generated from project.yml via XcodeGen)
├── SoundCompass              iOS 18+ app
├── SoundCompassWatch         watchOS 11+ companion
├── SoundCompassWatchWidgets  watchOS complication extension
├── SoundCompassWidgets       iOS Live Activity extension
└── SoundCompassTests         iOS XCTest bundle (69 tests)
```

All cross-platform code lives under `Shared/`. DSP lives under
`SoundCompass/DSP`. Services (audio, classifier, speech, watch,
live activity, passthrough, hazards, history, session stats) live
under `SoundCompass/Services`. Settings live under
`SoundCompass/Settings`. Motion lives under `SoundCompass/Motion`.
Calibration lives under `SoundCompass/Calibration`. Intents
(Siri / Shortcuts) live under `SoundCompass/Intents`.

The detailed DSP pipeline article is at
`SoundCompass/Documentation.docc/DSPPipeline.md`.

## What still needs real-hardware validation

The code compiles cleanly on Xcode 26 and all 69 DSP tests pass on
the iOS 26.4 simulator. What remains untested:

1. **Direction estimation on a real device** — the simulator's mono
   mic makes direction estimates meaningless. Clap left, clap right,
   verify the arrow swings correctly.
2. **CROS passthrough with headphones** — this is the single most
   useful feature for an SSD user and cannot be evaluated without
   headphones + a quiet room.
3. **Front/back disambiguation via rotation** — requires CoreMotion
   on a real device (the simulator has no gyroscope).
4. **Live Activity / Dynamic Island** — verify the Lock Screen
   widget appears and updates in real time.
5. **Watch companion** — pair and verify the compass mirrors.
6. **Sound classification** — Apple's built-in model might not be
   available on all device configurations.
